实验

实验 0　环境与基线

目标：装好驱动、ROCm 和 PyTorch；测出这块卡自己的带宽、算力和屋脊点（第 1 课的 roofline）；跑一个 Hugging Face 版 Qwen3-0.6B 作为后面所有实验的基线。

安装步骤按 AMD 官方文档 Install AMD ROCm 10.1.0（Ubuntu 26.04.1、apt 方式）编写，驱动部分按它指向的 AMD GPU Driver 31.60.0 文档，链接见参考资料。顺序是：前置条件 → 内核驱动 → ROCm → 检查 → PyTorch。

第 0 步：确认系统

  • 版本：Ubuntu 26.04.1 LTS（代号 resolute，内核 7.0）。ROCm 10.1.0 兼容性矩阵对 Radeon 列出的系统是 Ubuntu 26.04.1（GA 内核 7.0）、24.04.5（HWE 内核 7.0）和 22.04.5时效。RX 7000 系列（gfx1100 / gfx1101 / gfx1102）在支持列表里，RX 7800 XT 是 gfx1101，不需要网上常见的 HSA_OVERRIDE_GFX_VERSION。
  • Python：系统自带 Python 3.14，并且按 PEP 668 不允许直接往系统 Python 里 pip 装包，所以后面的 Python 包都装进 venv。AMD 的 PyTorch 支持 Python 3.11–3.14，直接用系统的 3.14。
  • 双系统：先在 Windows 里关掉“快速启动”；如果开了 BitLocker，先备份恢复密钥。
  • 磁盘：ROCm 装在 /opt/rocm/core-10.1，Docker 镜像默认在 /var/lib/docker，都在根分区上。最省事的是不把 / 和 /home 分开；分开的话要给 / 留足空间。全部装齐的保守估计见下表。
  • Secure Boot：如果开着，装驱动时会要求设一个 MOK 密码；重启时出现蓝色界面，选 Enroll MOK 并输入这个密码，否则驱动加载不了。
uname -m && cat /etc/*release   # 应看到 26.04、resolute
uname -srmv                     # 内核应是 7.0.x
python3 --version               # 应是 Python 3.14.x
df -h / /home                   # 各分区的可用空间

第 1 步：前置条件时效

部分 ROCm 工具需要 libatomic 和 libquadmath 两个库。GPU 访问权限有两种配法，官方文档都给了，二选一即可；本课程用方式 A（udev 规则）。

# 1) 部分 ROCm 工具需要的两个库
sudo apt update
sudo apt install -y libatomic1 libquadmath0

# 2) GPU 访问权限，二选一（第 2 步重启后生效）
# 方式 A（本课程采用）：udev 规则，本机所有用户都能访问 GPU
sudo tee /etc/udev/rules.d/70-amdgpu.rules << EOF
KERNEL=="kfd", GROUP="render", MODE="0666"
SUBSYSTEM=="drm", KERNEL=="renderD*", GROUP="render", MODE="0666"
EOF
sudo udevadm control --reload-rules
sudo udevadm trigger

# 方式 B：只给当前用户权限，加入 render、video 组
sudo usermod -a -G render,video $LOGNAME

方式 A 把 /dev/kfd 和 /dev/dri/renderD* 设成 0666，省去管理用户组，代价是本机所有账户和进程都能使用 GPU。单人使用的机器没问题；多人共用或要跑不受信任的服务时，改用方式 B，只给指定用户权限。

第 2 步：装内核驱动 AMD GPU Driver 31.60时效

ROCm 10.1.0 的文档要求 Instinct 和 Radeon 显卡安装 AMD GPU Driver（amdgpu）；兼容性矩阵对 Radeon 列出的驱动版本是 31.60.0 和 31.50.0。驱动通过 DKMS 为当前内核编译，所以要先装内核头文件。

# 1) 当前内核的头文件（DKMS 编译驱动模块要用）
sudo apt install -y "linux-headers-$(uname -r)"

# 2) 驱动软件源的签名密钥
sudo mkdir --parents --mode=0755 /etc/apt/keyrings
wget https://repo.radeon.com/rocm/rocm.gpg.key -O - | \
    gpg --dearmor | sudo tee /etc/apt/keyrings/rocm.gpg > /dev/null

# 3) 注册 amdgpu 31.60 软件源（resolute 是 26.04 的代号）
K=/etc/apt/keyrings/rocm.gpg
U=https://repo.radeon.com/amdgpu/31.60/ubuntu
sudo tee /etc/apt/sources.list.d/amdgpu.list << EOF
deb [arch=amd64 signed-by=$K] $U resolute main
EOF
sudo apt update

# 4) 装驱动，然后重启（第 1 步的权限设置也在这次重启后生效）
sudo apt install -y amdgpu-dkms
sudo reboot

第 3 段为了控制行宽用了两个 shell 变量，写进 amdgpu.list 的内容和官方文档一样。

第 3 步：装 ROCm 10.1.0时效

ROCm 10.1 换了新的软件源（stable.repo.amd.com）和包名（amdrocm10.1），旧版课程里的 amdgpu-install 脚本不再使用。磁盘充裕（见第 0 步的预算），本课程直接装完整套件 amdrocm-core-sdk10.1。

# 1) ROCm 软件源的签名密钥（和驱动的不是同一个）
sudo mkdir --parents --mode=0755 /etc/apt/keyrings
wget https://stable.repo.amd.com/rocm/gpg/packages.gpg -O - | \
    gpg --dearmor | sudo tee /etc/apt/keyrings/amdrocm.gpg > /dev/null

# 2) 注册 ROCm 软件源（deb822 格式的 .sources 文件）
sudo tee /etc/apt/sources.list.d/amdrocm-stable.sources << EOF
X-Repo-Id: amdrocm-stable
Types: deb
URIs: https://stable.repo.amd.com/rocm/core/packages/ubuntu2604/
Suites: stable
Components: main
Architectures: amd64
Signed-By: /etc/apt/keyrings/amdrocm.gpg
Enabled: yes
EOF
sudo apt update

# 3) 看可选的包名（包括只针对单一架构的版本）
apt-cache search amdrocm-core-sdk10.1

# 4) 完整套件（不加 -y：apt 先报占用空间，确认后再按 Y）
sudo apt install amdrocm-core-sdk10.1
#    只想最小安装就改成：sudo apt install amdrocm10.1

第 5 步：装 PyTorch 2.14.0时效

按 AMD AI Ecosystem 文档的 pip 装法，wheel 来自 AMD 的 whl-next 源。ROCm 10.1.0 兼容性矩阵列出的 PyTorch 是 2.14.0、2.13.0 和 2.12.0；这里选 2.14.0，原因见常见问题。

# 1) 建 venv（系统 Python 受 PEP 668 保护，不能直接 pip 装包）
sudo apt install -y python3-venv python3-pip
python3.14 -m venv ~/venvs/llm
source ~/venvs/llm/bin/activate
python -m pip install --upgrade pip

# 2) AMD 官方 wheel：PyTorch 2.14.0 + ROCm 10.1.0，gfx1101
python -m pip install \
    --index-url https://stable.repo.amd.com/rocm/whl-next/ \
    "torch[device-gfx1101]==2.14.0+rocm10.1.0" \
    "torchvision[device-gfx1101]==0.29.0a0+rocm10.1.0" \
    "torchaudio==2.11.0.3+rocm10.1.0"

# 3) 其余依赖从 PyPI 装
python -m pip install transformers safetensors

# 4) 应输出 True

device-gfx1101 是按官方页面的写法规律填的：选具体显卡时写 device- 加架构名，选“All”时写 device-all。如果 pip 提示 torch 不提供这个 extra，或者运行时报 invalid device function，就到 PyTorch 安装页依次选 ROCm 10.1.0、Radeon、RX 7800 XT、Linux、pip，按页面上的命令重装。

roofline.py：测出这块卡自己的 roofline。第 3 部分要求矩阵 W 大于显卡上 64 MB 的 Infinity Cache，否则测到的是缓存带宽，不是显存带宽。

import time
import torch

dev, dt = "cuda", torch.bfloat16


def bench(fn, iters=50, warmup=5):
    for _ in range(warmup):
        fn()
    torch.cuda.synchronize()
    t0 = time.perf_counter()
    for _ in range(iters):
        fn()
    torch.cuda.synchronize()
    return (time.perf_counter() - t0) / iters


# 1) 显存带宽：拷贝 1 GiB（读 1 GiB + 写 1 GiB）
a = torch.empty(2**29, device=dev, dtype=dt)
b = torch.empty_like(a)
t = bench(lambda: b.copy_(a))
bw = 2 * a.numel() * a.element_size() / t
print(f"copy bandwidth : {bw / 1e9:7.1f} GB/s")

# 2) 算力峰值：大矩阵乘
m = 8192
x = torch.randn(m, m, device=dev, dtype=dt)
w = torch.randn(m, m, device=dev, dtype=dt)
t = bench(lambda: x @ w, iters=20)
peak = 2 * m**3 / t
print(f"bf16 GEMM peak : {peak / 1e12:7.1f} TFLOPS")
print(f"ridge point    : {peak / bw:7.1f} FLOP/byte")

# 3) 模拟 decode：Y = X(B×d) @ W(d×d)，扫描 batch 大小 B
#    d=8192 时 W 有 128 MiB，比 64 MB 的 Infinity Cache 大
d = 8192
w = torch.randn(d, d, device=dev, dtype=dt)
print("    B   time(us)  TFLOPS  FLOP/byte")
for B in [1, 2, 4, 8, 16, 32, 64, 128, 256, 512, 1024, 2048]:
    x = torch.randn(B, d, device=dev, dtype=dt)
    t = bench(lambda: x @ w)
    flops = 2 * B * d * d
    nbytes = 2 * (d * d + 2 * B * d)
    print(f"{B:5d} {t * 1e6:10.1f} {flops / t / 1e12:7.2f}"
          f" {flops / nbytes:10.1f}")

hf_baseline.py：Hugging Face 版 Qwen3-0.6B 的基线，后面自己写的引擎都和它比。

import sys
import time
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

# 用法：python hf_baseline.py <roofline.py 测到的带宽 GB/s>
bw = float(sys.argv[1]) * 1e9 if len(sys.argv) > 1 else None
mid = "Qwen/Qwen3-0.6B"
tok = AutoTokenizer.from_pretrained(mid)
model = AutoModelForCausalLM.from_pretrained(
    mid, dtype=torch.bfloat16).to("cuda").eval()

nbytes = sum(p.numel() * p.element_size() for p in model.parameters())
print(f"weights: {nbytes / 1e9:.2f} GB")

prompt = "Explain how a KV cache speeds up decoding. " * 20
enc = tok(prompt, return_tensors="pt").to("cuda")
n_in = enc.input_ids.shape[1]
print("prompt tokens:", n_in)


@torch.no_grad()
def run(n_new):
    torch.cuda.synchronize()
    t0 = time.perf_counter()
    out = model.generate(**enc, max_new_tokens=n_new,
                         min_new_tokens=n_new, do_sample=False)
    torch.cuda.synchronize()
    return time.perf_counter() - t0, out


run(8)                    # 预热
t1, _ = run(1)            # ≈ prefill + 第 1 个 token
t2, out = run(129)
tpot = (t2 - t1) / 128
print(f"TTFT ≈ {t1 * 1e3:.1f} ms")
print(f"TPOT ≈ {tpot * 1e3:.2f} ms  ({1 / tpot:.0f} tok/s)")
if bw:
    bound = nbytes / bw
    print(f"带宽上限 ≈ {bound * 1e3:.2f} ms/token"
          f"  ({1 / bound:.0f} tok/s)")
print(tok.decode(out[0, n_in:n_in + 40]))

运行顺序：python check_env.py，然后 python roofline.py，最后 python hf_baseline.py <roofline.py 测到的带宽>。

大致预期

  • check_env.py：torch 版本带 +rocm10.1.0；arch 显示 gfx1101；显存约 16 GiB；按 AMD 的说明，PyTorch 2.14 在这类显卡上默认用 hipBLASLt，BLAS 一行应显示 Cublaslt。
  • roofline.py：带宽接近但低于标称的 624 GB/s；BF16 矩阵乘达不到标称的 74.65 TFLOPS，这是正常的；按标称参数算，屋脊点约 120 FLOP/字节（H100 是 295）。扫描 batch 大小时，B 很小的阶段耗时几乎不变（带宽瓶颈），越过屋脊点附近以后耗时开始随 B 线性增长。
  • hf_baseline.py：实测 TPOT 可能比带宽上限慢很多，原因留给思考题 3。

思考题

  1. 你实测的屋脊点是多少？和按标称参数算的约 120 差多少？差距主要来自带宽还是算力？

实验 1　手写 Qwen3 前向

目标：不用 transformers 的模型代码，自己从 safetensors 读权重、写出 Qwen3-0.6B 的完整前向，和 Hugging Face 的结果对齐；再加上 KV cache 和采样。对应第 1 课、问 4.3–4.8 和第 7.1 节。
Qwen3-0.6B 配置数值写代码时要注意
hidden_size / 层数1024 / 28
Q head / KV head / head_dim16 / 8 / 128Q 投影是 1024 → 2048，比 hidden 大；每 2 个 Q head 共用 1 个 KV head
MLP 中间维度3072SwiGLU：gate、up、down 三个矩阵
词表151,936lm_head 与 embedding 共享权重（tie_word_embeddings）
RoPE θ / RMSNorm ε1,000,000 / 1e-6Q、K 先做逐 head 的 RMSNorm（QK-Norm）再加 RoPE
每 token 的 KV112 KiB（BF16）2 × 28 层 × 8 个 KV head × 128 × 2 字节

一层的计算（伪代码）：

x = embed_tokens[ids]                         # [T, 1024]
for layer in range(28):
    h = rmsnorm(x, input_layernorm)
    q = h @ q_proj.T  -> [T, 16, 128] -> q_norm -> RoPE
    k = h @ k_proj.T  -> [T,  8, 128] -> k_norm -> RoPE
    v = h @ v_proj.T  -> [T,  8, 128]
    a = causal_attention(q, k, v)  # 每 2 个 Q head 共用 1 个 KV head
    x = x + a.reshape(T, 2048) @ o_proj.T
    h = rmsnorm(x, post_attention_layernorm)
    x = x + (silu(h @ gate_proj.T) * (h @ up_proj.T)) @ down_proj.T
logits = rmsnorm(x, norm) @ embed_tokens.T    # lm_head 与 embedding 共享

要做的事

  1. 读权重：用 safetensors 读出所有张量，打印名字和形状，对照下面的配置弄清每个张量的作用。
  2. 写前向：Embedding → 28 层（RMSNorm → attention → 残差 → RMSNorm → MLP → 残差）→ 最后的 RMSNorm → lm_head。attention 里包含 QK-Norm、RoPE、GQA 和因果 mask。
  3. 对齐：用 Hugging Face 的 output_hidden_states=True 逐层对比；BF16 下有小误差是正常的，可以先在 FP32 下对齐再切回 BF16。
  4. 生成循环：先写不带 cache 的版本（每一步重算全部 token），再写 KV cache 版本（预分配 [层, 2, 最大长度, KV head, head_dim]，prefill 写入，decode 每步追加 1 个）。
  5. 采样：greedy、temperature、top-k、top-p。

完成标准

  • 同一个 prompt 贪心生成 64 个 token，输出和 Hugging Face 完全一致。
  • 画出 TPOT 随上下文长度的变化：不带 cache 时持续上升，带 cache 时基本平稳。
  • KV cache 实际占用的显存和 112 KiB/token 的估算一致。

思考题

  1. 不带 cache 时，第 n 步大约要算多少？为什么 TPOT 随长度增长？
  2. 4K 上下文的一个请求，KV cache 有多大？16 GB 的卡除去权重，能同时放下多少个这样的请求？
  3. 你的 TPOT 离实验 0 的带宽上限还差多少？差在哪里？

  • tiny-llm：基于 MLX 的“一周写一个推理服务”课程，可作为章节安排的参考

实验 2　引擎核心：调度、分页 KV、前缀缓存

目标：把单请求的生成循环改造成能同时服务很多请求的引擎。对应第 2 课。

要做的事

  1. 请求状态机：等待 → 运行 → 完成，以及被抢占后回到等待。
  2. 调度器：每一步给 prefill 和 decode 分配 token 预算，实现 continuous batching（第 2 课）。
  3. Block manager：每块 16 个 token，空闲列表加引用计数；每个请求一张 block table。
  4. 分页 attention：先用 PyTorch 按 block table 把 KV 收集出来再算，正确性优先，性能留给实验 3。
  5. 前缀缓存：块哈希链 + 引用计数 + LRU 淘汰（第 2 课问 2.2）。
  6. 抢占：显存不够时回收某个请求的块，之后重算（第 2 课的“抢占”）。
  7. chunked prefill：把长 prompt 切成多段，和 decode 混在同一步里。

完成标准

  • 单请求输出和实验 1 完全一致。
  • 100 个长度不一的请求，吞吐明显高于静态 batching。
  • 多个请求共用一段 system prompt 时，后面请求的 TTFT 明显下降。

思考题

  1. block 大小取 16 和取 128，各有什么利弊？
  2. 前缀缓存命中率很高时，显存里最占地方的是什么？该先淘汰谁？
  3. 混入一个很长的 prefill 时，decode 请求的 ITL 会怎样？chunked prefill 怎么缓解？

参考

  • nano-vllm：约 1,200 行 Python 的 vLLM 简化实现，调度器、block manager、前缀缓存都很短

实验 3　性能优化：kernel、量化、Graph、投机解码

目标：把实验 2 的引擎跑快，并用实测数据验证第 3 课的结论。

要做的事

  1. 用 Triton 写分页 decode attention：按 block table 读 KV，用 online softmax（问 3.1）一遍算完；再写融合的 RMSNorm + 残差、写入 KV cache 的 kernel。
  2. INT8 权重量化：按输出通道存缩放系数，decode 时边读边反量化。7800 XT 没有 FP8 硬件，所以这里用 INT8。
  3. HIP Graph：给几个固定的 batch 尺寸录制 decode 步，重放时省掉 kernel 启动开销（PyTorch 的 CUDA Graph 接口在 ROCm 上对应 HIP Graph）。
  4. 投机解码：Qwen3-0.6B 当草稿模型、Qwen3-4B 当目标模型（4B 的 BF16 权重约 8 GB，放得下）；统计接受率。
  5. 用 torch.profiler 找瓶颈，每做一项优化都记下前后数据。

完成标准

  • 每个 kernel 的结果和 PyTorch 参考实现对齐。
  • decode TPOT 逐步下降，并能说清每一步省下的是什么（访存、计算还是启动开销）。
  • 投机解码实测的每步产出 token 数，和公式 (1 − αk+1) / (1 − α) 对得上（第 3 课问 3.2）。

思考题

  1. INT8 量化让 decode 变快了多少？为什么 prefill 几乎没变快？
  2. HIP Graph 对小 batch 和大 batch 的收益为什么不同？
  3. 草稿模型猜 k = 2、4、8 个时，实测加速比怎么变？最优的 k 是多少？

参考

  • nano-vllm-lite：在 nano-vllm 基础上加了 CUDA Graph、chunked prefill、FP8 KV cache，每项优化都有实测数据
  • nano-vllm：约 1,200 行 Python 的 vLLM 简化实现，调度器、block manager、前缀缓存都很短

常见问题

  • torch.cuda.is_available() 返回 False：依次检查 GPU 访问权限（udev 方式看 ls -l /dev/kfd /dev/dri/renderD* 是否显示 crw-rw-rw-；加组方式看 groups 里有没有 render 和 video，加组后要重启）；dkms status 里 amdgpu 是不是 installed；rocminfo 能不能看到 gfx1101；pip show torch 的版本号是否带 +rocm10.1.0，而不是 PyPI 上的普通版。
  • udev 规则没生效（显示 crw-rw----）：检查规则文件里的引号是不是英文直引号，再执行 sudo udevadm control --reload-rules 和 sudo udevadm trigger，或者直接重启。
  • pip 报 externally-managed-environment：Ubuntu 26.04 的系统 Python 受 PEP 668 保护。先 source ~/venvs/llm/bin/activate 再装。
  • 为什么选 PyTorch 2.14.0：AMD 的已知问题写明，PyTorch 2.14 之前，RX 7900 系列、RX 7800 XT 等显卡上部分 LLM 推理负载（包括 batch 不小于 8 的 vLLM FP16 decode）性能偏低，临时办法是设 TORCH_BLAS_PREFER_HIPBLASLT=1；从 2.14 起这是这些显卡的默认设置。如果别的工具要求 2.13，记得设这个环境变量。
  • 后装的包把 torch 换掉了：在这个 venv 里装依赖 torch 的包时，pip 可能从 PyPI 拉另一个 torch。装之前先用 pip install --dry-run 看会不会动 torch。
  • 开了 Secure Boot，驱动加载不了：amdgpu-dkms 是 DKMS 编译的内核模块，装的时候留意 MOK 密码提示，重启时选 Enroll MOK。
  • amdgpu-dkms 编译失败，或升级内核后驱动没了：先装当前内核的头文件 sudo apt install "linux-headers-$(uname -r)"，再重装 amdgpu-dkms。
  • 之前照旧版课程装过 ROCm 7.2.1：AMD 驱动文档要求先卸掉之前装的驱动（旧版用 sudo amdgpu-uninstall）。旧的 amdgpu-install 脚本和 rocm-rel-7.2.1 的 wheel 都不适用于 ROCm 10.1。全新安装的 26.04.1 不用管这条。
  • 不需要 HSA_OVERRIDE_GFX_VERSION：gfx1101 在 ROCm 10.1.0 的支持列表里。
  • 主流引擎能跑吗：上面那条已知问题提到了 RX 7800 XT 上的 vLLM，说明 AMD 在这块卡上跑过 vLLM。兼容性矩阵里 ROCm 10.1.0 对应 vLLM 0.29.0，要求 PyTorch 2.13.0。可以在实验 6 拿它当对照基线，单独建一个 venv，不要装进主环境。
  • 卸载：ROCm 用 sudo apt autoremove amdrocm-core-sdk10.1（只装了基础包就换成 amdrocm10.1），再删 /etc/apt/sources.list.d/amdrocm-stable.sources、清理 apt 缓存；驱动用 sudo apt autoremove amdgpu-dkms，再删 /etc/apt/sources.list.d/amdgpu.list、清理缓存后重启。
  • 看磁盘占用：du -sh /opt/rocm/core-10.1 ~/venvs ~/.cache/huggingface 看 ROCm、Python 环境和模型各占多少；docker system df 看 Docker 镜像。
  • 显存不够：先用 Qwen3-0.6B，缩短最大长度、减小 batch。
  • Qwen3 默认开着思考模式：做速度测试时直接喂原始文本即可，不必套聊天模板。模型卡提醒思考模式下贪心解码容易无限重复，这不影响测速，但看输出质量时要换成推荐的采样参数。
