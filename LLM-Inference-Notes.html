三个核心矛盾

  1. 吞吐与延迟：batch 越大，GPU 用得越充分、越省钱，但每个请求等得越久。
  2. 显存：权重和 KV cache 抢同一块显存；上下文越长、并发越多，KV 越大。
  3. prefill 与 decode：一个吃算力、一个吃带宽，放在一起会互相干扰。

后面 6 课的各种技术，基本都是在这三个矛盾之间找平衡。

第 1 课　推理基础：prefill、decode、KV cache 与 roofline

一句话：一个请求分两个阶段。prefill 一次性处理整段 prompt，受算力限制，决定首 token 时间（TTFT）；decode 每次生成一个 token，每一步都要把全部权重和 KV 从显存读一遍，受带宽限制，决定 token 间延迟（ITL，也常写作 TPOT）。

KV cache：用显存换计算

生成下一个 token 时，要用到前面所有 token 在每一层的 K 和 V。把它们存下来，就不必每一步都重算整段上下文。代价是显存：

每个 token 的 KV 字节数 = 2（K 和 V）× 层数 × KV head 数 × head_dim × 每个数的字节数

Llama-3.1-8B（BF16）：  2 × 32 × 8 × 128 × 2 = 131,072 字节 = 128 KiB
Llama-3.1-70B（BF16）： 2 × 80 × 8 × 128 × 2 = 327,680 字节 = 320 KiB
8B 的一个 4K 上下文请求：4,096 × 128 KiB = 512 MiB ≈ 0.537 GB

单位：KiB、MiB、GiB 是 1024 进制；GB、GB/s、FLOP 是 1000 进制。先换成字节，再去除带宽。

Roofline：算力瓶颈还是带宽瓶颈

算术强度 = 计算量 ÷ 访存字节数。H100 的"屋脊点"是 989.4 TFLOPS ÷ 3.35 TB/s ≈ 295 FLOP/字节时效：算术强度低于它就受带宽限制，高于它才受算力限制。

问 1.1「decode 的算术强度为什么约等于 batch 大小 B？」（大意） 看解答 ↓
一个 d × d 的线性层，这一步有 B 个 token（BF16，每个权重 2 字节）：
  计算量 = 2 × B × d²   FLOP
  读权重 = 2 × d²       字节
  算术强度 ≈ B          FLOP/字节

decode： B 是 batch 里的请求数，通常远小于 295 → 带宽瓶颈
prefill：B 是 prompt 的 token 数（成百上千） → 算力瓶颈

两个下限

decode 每步时间下限 ≈ (全部权重字节 + 这一步要读的全部 KV 字节) / 显存带宽
prefill 时间下限    ≈ 2 × 参数量 × prompt 的 token 数 / 峰值算力

8B，batch 1：           16.06 GB / 3.35 TB/s ≈ 4.79 ms
8B，2,000 token 的 prompt：2 × 8.03e9 × 2,000 / 989.4e12 ≈ 32.5 ms
8B，batch 64、每个 4K 上下文：
  (16.06 + 64 × 0.537) GB / 3.35 TB/s ≈ 15.05 ms，每秒合计约 4,252 个 token
  • batch 越大，同一次读权重分摊给越多请求，总吞吐越高；但 KV 也随 batch 线性增长，最终会先撞上显存容量或 ITL 目标。
  • 这就是第 0 课"吞吐与延迟""显存"两个矛盾的根源。

第 2 课　推理引擎：continuous batching、PagedAttention 与前缀缓存

一句话：引擎每一步都重新组 batch（continuous batching），用分页的方式管理 KV 显存（PagedAttention），并让前缀相同的请求共享 KV（前缀缓存）。

Continuous batching

早期按"请求"组 batch：一批里先结束的也得等全批跑完，新请求要等下一批。Orca 提出按"迭代"调度：每生成一个 token 就重新决定 batch 里有谁，结束的马上离开，新来的马上加入。

问 2.1「为什么一个请求在做 prefill，会让同一批里别人的 decode 变慢？」（大意） 看解答 ↓
每一步是一个同步点：batch 里所有请求都算完这一步，大家才拿到下一个 token

8B，100 个请求（每个约 2K 上下文）纯 decode：      每步约 12.81 ms
同一步里插进一整段 32K token 的 prefill：            这一步约 0.82 秒
chunked prefill（长 prompt 切块，与 decode 拼进同一步）：每步约 34–65 ms

chunked prefill（SARATHI）把长 prompt 切成多块，与 decode 混在同一步里跑：块越小，ITL 越稳，但 TTFT 越长。第 5 课的 P/D 分离是另一种解法。

PagedAttention

  • 像操作系统的虚拟内存分页：KV 存放在固定大小的块（block，常见 16 个 token）里，每个请求用一张"块表"把逻辑位置映射到物理块。用多少分配多少，几乎没有碎片。
  • 8B 的一个 16 token 块：16 × 128 KiB = 2 MiB。
  • vLLM 论文报告：在相同延迟下，吞吐比 FasterTransformer 和 Orca 高 2–4 倍。

前缀缓存

  • 每个块按"前面所有 token + 本块 token（再加上 LoRA、多模态、cache_salt 等额外信息）"算哈希，哈希相同就复用同一块物理 KV。
  • 只能共享内容完全相同的整块。

抢占

显存不够时，调度器会把一些请求踢回等待队列；vLLM V1 默认丢掉它们的 KV，之后重算时效。抢占不会报错，只会让一部分请求的尾延迟变差，所以要监控抢占次数（第 6 课）。

第 3 课　单卡优化：FlashAttention、量化、CUDA Graph 与投机解码

一句话：四种优化各对付一个瓶颈：FlashAttention 减少 attention 的显存读写；量化减少要搬的字节；CUDA Graph 去掉 CPU 发射 kernel 的开销；投机解码让一次读权重产出多个 token。

FlashAttention

普通实现会把 N × N 的注意力分数矩阵写回显存、再读出来，长序列时这部分读写就是瓶颈。FlashAttention 把 Q、K、V 切块放进片上 SRAM，边算边做 softmax，不把这个大矩阵落到显存；计算量不变，结果完全精确。

问 3.1「分块计算 softmax，为什么结果和整行一起算完全一样？」（大意） 看解答 ↓
把一行分数分成两块，分别算出：
  块 1：最大值 m1，指数和 l1 = Σ exp(s − m1)，按块内 softmax 加权的输出 o1
  块 2：最大值 m2，指数和 l2，输出 o2
合并：
  m = max(m1, m2)
  l = exp(m1 − m) · l1 + exp(m2 − m) · l2
  o = [exp(m1 − m) · l1 · o1 + exp(m2 − m) · l2 · o2] / l
与一次性对整行做 softmax 的结果完全相等

量化

  • 权重量化（FP8、INT4）：decode 受带宽限制，要搬的字节减半，时间就近似减半。
8B，batch 1 的 decode 每步下限：
  BF16：16.06 GB → 4.79 ms
  FP8：  8.03 GB → 2.40 ms
  INT4：约 4 GB  → 1.20 ms（不计缩放系数）
  • 计算也用 FP8时，H100 峰值从 989.4 翻倍到 1,979 TFLOPS，prefill 才会明显变快；只量化权重、计算仍用 BF16，对 prefill 帮助不大。
  • KV cache 量化（如 FP8）：KV 减半，能放下更多并发，每步读得也更快。
  • 代价是精度可能下降，要用评测验证。

CUDA Graph

decode 一步要发射几百个小 kernel。batch 小、每步只有几毫秒时，CPU 一个个发射 kernel 的开销占比可观。CUDA Graph 把整步的 kernel 序列录制一次，之后整体重放，省掉这部分开销。限制是形状要固定，所以引擎会按几种常见的 batch 大小分别录制。

投机解码

先用一个小的草稿模型猜 k 个 token，再让大模型一次前向同时验证。decode 受带宽限制，验证 k 个和生成 1 个的耗时差不多，所以猜中越多越赚；配合拒绝采样，输出分布与原模型完全一致。

每个草稿 token 被接受的概率为 α，一次猜 k 个：
  每步期望产出的 token 数 = 1 + α + α2 + … + αk
                          = (1 − αk+1) / (1 − α)
例：α = 0.8，k = 4 → 约 3.36 个

第 4 课　分布式推理与 MoE：DP、TP、PP、EP

一句话：模型一张卡放不下，或者单卡跑得太慢，就要切到多张卡上。四种切法的区别在于"切什么"和"每一步要通信什么"；通信越频繁、量越大的切法，越要放在越快的互联上。

问 4.1「DP/TP/PP/EP是什么的缩写？」 看解答 ↓
切法切什么每一步通信什么一般放在哪
DP（数据并行）整个模型复制多份，各自处理不同请求几乎不通信任意位置
TP（张量并行）每一层的矩阵切到多张卡每层 2 次 all-reduce机内（NVLink）
PP（流水线并行）按层切成几段，像流水线一样接力段与段之间传激活可以跨机
EP（专家并行）MoE 的不同专家放到不同卡每个 MoE 层 2 次 all-to-all机内 + 跨机高速网络

为什么要切

  • 放不下：70B 的 BF16 权重有 141.2 GB，一张 80 GB 的卡装不下。
  • 太慢：decode 每步的下限约等于"每张卡要读的权重字节 ÷ 带宽"。
70B BF16 放在一张（假想的）足够大的卡上：141.2 GB / 3.35 TB/s ≈ 42.1 ms
TP=8，每张卡只读 1/8：                   17.65 GB / 3.35 TB/s ≈ 5.27 ms

一层里有什么

问 4.3「解释一下TP里的每一层是指什么？以transformer based模型为例，每一层对应softmax（Q*K*缩放）*Vt的哪一个？」 看解答 ↓

TP：把每一层切开（Megatron-LM）

MLP 的 TP 切法（n 张卡）：
  W_up 按列切成 n 份，W_down 按行切成 n 份，第 b 份放在第 b 张卡
  Y = act(X · W_up) · W_down
    = act(X · W_up_1) · W_down_1 + … + act(X · W_up_n) · W_down_n
  每张卡只算自己那一项，最后 all-reduce 求和
Attention 同理：按 head 切，每张卡负责一部分 query head 和对应的 KV head

问 4.4「理论上每一层的输入应该是上一层完整的输出对吗？那在TP里是不是每个GPU都要先算完第i层的部分输出，然后所有gpu的输出汇总成完整的输出，再执行下一层？」 看解答 ↓

每层要做两次 all-reduce：attention 的输出投影之后一次，MLP 的 W_down 之后一次。70B 有 80 层，每步就是 160 次；按每次约 10 µs 算，约 1.6 ms。这就是 TP 要放在 NVLink 这种机内高速互联上的原因。

GQA

问 4.8「GQA是什么」 看解答 ↓

多个 query head 共用一组 K、V。Llama-3.1-8B 有 32 个 query head、8 个 KV head；70B 有 64 个 query head、8 个 KV head。KV 大小因此分别降到原来的 1/4 和 1/8。TP=8 时，正好每张卡分到 1 个 KV head。

PP

按层切成几段。单个请求要依次走完所有段，所以 batch 1 的延迟不会降低；但多个微批可以同时在不同段上跑，吞吐能接近 TP。通信只在段与段之间传激活，量小，适合跨机。

MoE 与 EP

问 4.9「EP没太看懂，重讲一次」 看解答 ↓
  • MoE：每层有很多个"专家" MLP，每个 token 只选其中几个（top-k）。DeepSeek-V3 总参数 671B，每个 token 只激活 37B。
  • 每个专家只分到 batch 的一小部分：平均是 batch 的 k/E。Mixtral 风格（8 选 2）是 1/4，DeepSeek-V3（256 选 8）是 1/32。专家要分到约 295 个 token（H100 的屋脊点）时效才不受带宽限制，所以细粒度 MoE 需要非常大的 batch。
  • EP：把专家分散到很多张卡上，每张卡上的专家收集所有卡送来的 token，才凑得够 batch。每个 MoE 层两次 all-to-all：先把 token 分发到专家所在的卡，算完再送回来合并。
  • DeepSeek 的线上部署：prefill 单元用 4 台机器（EP32），decode 单元用 18 台（EP144）。

第 5 课　集群层：KV 感知路由、P/D 分离与分布式 KV cache

一句话：到了集群层，问题变成三件事：请求发给哪个实例（KV 感知路由），prefill 和 decode 要不要分开部署（P/D 分离），KV 存在哪里、能不能跨实例复用（分布式 KV cache）。三件事都围绕 KV cache 展开——Mooncake 就把自己的架构称为"以 KV cache 为中心"。

用户请求
  ↓
Gateway：鉴权、限流
  ↓
Router：查全局 KV 索引，选一个"命中多、又不太忙"的 prefill 实例，
        再选一个显存有余量的 decode 实例
  ↓
Prefill 实例：
  命中 GPU 前缀缓存的部分：直接复用
  命中 CPU 内存、SSD 或远端 KV 池的部分：加载回 GPU（比重算快）
  剩下的部分：计算；每算完一层，就把这一层的 KV 通过 RDMA 发给 decode 实例
  ↓
Decode 实例：收到 KV 后加入 continuous batching，逐个生成 token，流式返回
  ↓
请求结束：KV 留在缓存里，或写入分层存储，供下一轮对话复用

KV 感知路由

  • 请求是有状态的：发给缓存了它前缀的实例，就能跳过这部分 prefill。
  • 影响集群的有效缓存容量：随机分配时，每个实例都得缓存所有热门前缀，有效缓存只相当于一个实例；按缓存路由时，有效容量接近所有实例之和。
  • 路由器怎么知道谁缓存了什么：近似做法按自己发出过的请求，为每个实例维护一棵前缀树（如 SGLang）；精确做法由引擎上报 KV 事件，汇总成全局索引（如 Dynamo、llm-d）。
  • 命中和负载要一起看，Dynamo 的代价函数时效：
prefill 项 = 积压 + 新请求的输入 − 新请求的缓存命中（都按块数计）
  积压：已经派到这个实例、还没出第一个 token 的请求，它们还要算的 prompt token
decode 项  = 这个实例上所有活跃请求占用的 KV 块数 + 新请求将要占用的块数
cost = 权重 × prefill 项 + decode 项，选 cost 最小的实例

例（请求共 10 块，权重 1.0）：
  实例 1：积压 0， 命中 2，decode 10 → (0 + 10 − 2) + 10 = 18
  实例 2：积压 12，命中 5，decode 5  → (12 + 10 − 5) + 5 = 22
  实例 3：积压 0， 命中 8，decode 9  → (0 + 10 − 8) + 9  = 11  ← 选中

P/D 分离

  • 为什么：两个阶段会互相干扰（第 2 课的数字）；需要的资源不同，prefill 吃算力、decode 吃带宽和 KV 显存；硬件也可以不同（Splitwise）。
1. Router 选一对实例：prefill 实例 P、decode 实例 D
2. P 做 prefill，算出第一个 token
3. P 把这个请求的 KV 发给 D（可以算完一层发一层）
4. D 把请求加入自己的 decode batch，继续生成，流式返回

第 6 课　生产化：SLO、扩缩容、过载保护、可观测性与多租户安全

一句话：前 5 课解决的是"跑得快、跑得省"，生产环境还要"在真实流量下跑得稳"：流量有涨有落，要自动扩缩容；资源总有不够的时候，要定 SLO、留余量、做过载保护；出了问题要看得见，要可观测性；很多客户共用一套系统，要多租户隔离与安全。

用户请求
  ↓
网关：鉴权、按租户注入身份和优先级、按 token 计的配额
  ↓
准入控制：系统快满时，按优先级排队，可丢弃的请求直接拒绝
  ↓
路由 → prefill 池 / decode 池（第 5 课）
  ↓
可观测性：每一步都打指标和追踪；扩缩容控制器根据指标增减两个池

SLO 与 goodput

  • SLO 用分位数，不用平均值：常见的是 TTFT 和 ITL 的 P90 或 P99。比如 Dynamo Planner 的默认目标是 TTFT 500 ms、ITL 50 ms时效。平均值会把尾部的慢请求藏起来。
问 6.1「ITL是啥缩写？」 看解答 ↓
  • 要优化的是 goodput：Mooncake 的标准是只有完整跑完的请求才计数；跑不完的请求，之前算过的 token 全部白费，所以没法在 SLO 内跑完的请求应该尽早拒绝。
  • 一定要留余量：越接近满载，排队时间涨得越陡。
平均排队时间 / 处理一个请求的时间 = ρ / (1 − ρ)（ρ 是利用率，M/M/1 模型）

  利用率 50%：1.0 倍
  利用率 70%：2.3 倍
  利用率 80%：4.0 倍
  利用率 90%：9.0 倍
  利用率 95%：19.0 倍

LLM 引擎有 batching，不完全符合这个模型，但"越接近满载、延迟越陡"的规律一样。vLLM 文档把这个拐点叫作饱和点：再增加请求，吞吐不再上升，只是延迟变长。

Little 定律：系统里同时在处理的请求数 = 到达速率 × 每个请求停留的时间

例：每秒 20 个请求，每个输出 400 token，ITL 25 ms
  每个请求的 decode 时间 = 400 × 25 ms = 10 秒
  同时在 decode 的请求数 = 20 × 10 = 200 个

自动扩缩容

  • 不能照搬 Web 服务：LLM 的延迟取决于请求内容而不只是请求数，一个 32K token 的 prompt 消耗的算力比短请求多几个数量级；prefill 随输入长度增长、decode 随并发和 KV 占用增长，一个副本数没法同时描述两者。
  • 不要按 GPU 利用率扩缩容：nvidia-smi 的 GPU 利用率是采样周期内"至少有一个 kernel 在运行"的时间占比，不是算力用了多少；decode 受带宽限制，这个数字照样可能接近 100%。要看效率，得看 DCGM 的 SM 活跃比例和 Tensor Core 活跃比例。
池主要看vLLM 里对应的指标时效
prefill 池排队的请求、TTFTvllm:num_requests_waiting、vllm:time_to_first_token_seconds
decode 池KV 占用、ITL、正在跑的请求数vllm:kv_cache_usage_perc、vllm:inter_token_latency_seconds、vllm:num_requests_running
  • Dynamo Planner：按 TTFT 和 ITL 目标分别调整 prefill 和 decode 的 worker 数；基于吞吐的模式结合流量预测、默认每 180 秒调一次，基于负载的模式默认每 5 秒调一次以应对突发时效；两者一起开时，前者给容量下限，后者在下限之上做实时调整。

过载保护

  • 按 token 计配额，而不是按请求数：VTC（OSDI 2024）指出，按每分钟请求数限流会在系统空闲时也把客户挡在外面；2K token 和 200 token 的请求消耗差很多，应按 token 统计服务量、做公平调度。
  • 优先级和可丢弃请求：Gateway API Inference Extension 用整数表示优先级，数字越大越优先，负数表示"可丢弃"，系统饱和时直接拒绝；vLLM 引擎的 --scheduling-policy priority 约定相反，数字越小越优先，并可抢占低优先级的请求。
  • 提前拒绝（Mooncake）：做完 prefill 才被 decode 实例拒绝，算力就白花了，所以在 prefill 开始前就按两个池中更高的负载决定接不接；这会引起两个池负载的反相波动，于是进一步预测输出长度和短期负载。
  • 降级：限制 max_tokens、切到小模型、排队设超时、返回 429 并带上 Retry-After。
  • 优先级和租户身份不能让客户端自己说了算：由可信网关剥离外部头、按 API key 重新注入（和第 2 课 cache_salt 同理）。

第 7 节　延伸：新架构与新负载

一句话：主流大模型的骨架仍是 Transformer，但 MLP 普遍换成了 MoE，attention 分化成标准、稀疏或压缩、混合线性三条路线。推理系统里和权重、调度有关的部分基本不变；围绕 KV 的机制要扩展成“KV + 状态”。agent 的上下文压缩发生在客户端或 API 层，要和引擎的前缀缓存配合着用。

7.1 Transformer 不等于 attention

问 7.1「我可以把transformer结构等同于attention吗？」 看解答 ↓

attention 是 Transformer 里负责“token 之间交换信息”的那一块，另一块 MLP 负责“每个 token 各自加工”。一层 = attention + MLP，再用残差和 RMSNorm 串起来（问 4.5 里的理解是对的）。

输入 token → Embedding（查表变成向量）
重复 32 层（Llama-3.1-8B），每层两块：
  h = x + Attention(RMSNorm(x))   ← token 之间交换信息
  y = h + MLP(RMSNorm(h))         ← 每个 token 各自加工
→ RMSNorm → lm_head → 下一个 token 的概率
部件负责什么8B 参数占比
Attention 块（Q/K/V/O 投影 + 打分加权）token 之间交换信息16.7%
MLP 块（SwiGLU）每个 token 各自加工70.2%
Embedding + lm_headtoken 和向量互相转换13.1%
RMSNorm、残差、RoPE稳定数值、帮助训练深层网络、提供位置信息几乎为 0
  • “Attention Is All You Need”的意思是：token 之间交换信息只靠 attention，不再用 RNN 或卷积。原版 Transformer 同样有 MLP（论文里叫 FFN）、残差、LayerNorm 和位置编码，而且是 encoder + decoder 结构；现在的 LLM 大多只保留 decoder。attention 本身也不是 Transformer 发明的，2014 年就用在 RNN 翻译模型里了。
  • 对推理的意义：权重的大头在 MLP，decode 每步读权重主要读的是 MLP，MoE 替换的也是 MLP；KV cache 只属于 attention，因为 MLP 只看当前 token，没有跨 token 的状态；以 8B 为例，decode 时上下文不到约 2.7 万 token，计算大头在线性层（MLP 加 attention 的四个投影），更长时 attention 的打分和加权求和才反超；TP 时 attention 按 head 切，MLP 把 W_up 按列、W_down 按行切。

7.2 2025 年之后的主流模型时效

问 7.2「那2025年之后的主流模型都是transformer架构吗？」 看解答 ↓

骨架基本都还是 Transformer，但“每一层都是标准 attention”已经不是唯一主流。大模型的 MLP 大多换成了 MoE，变化集中在 attention 那一半。下面都是公开了结构的开源模型，闭源旗舰大多不公开这些细节。

路线做法代表模型
标准 Transformer每层都是 softmax attention（GQA 或 MLA）gpt-oss、MiniMax M2
改造 attention每层仍是 attention，但只看一部分 token，或者把 KV 压缩DeepSeek-V3.2、DeepSeek-V4
混合架构大部分层换成线性 attention 或 Mamba，只保留少数 full attention 层Qwen3-Next、Qwen3.5、Kimi Linear、Nemotron 3
  • 标准：gpt-oss 是在 GPT-2、GPT-3 架构基础上做的 MoE Transformer；MiniMax M2 是 62 层的 decoder-only Transformer，62 层全部用 GQA。
  • 改造 attention：DeepSeek-V3.2 的 DSA 先用轻量的 lightning indexer 给前文打分，每个 query 只看得分最高的 2,048 个 token——MLA 让每条 KV 变小，DSA 减少每次要读的条数。DeepSeek-V4（2026 年 4 月）把 CSA 和 HCA 两种压缩 attention 混合使用，还把标准残差连接换成了 mHC；1M 上下文下，每生成一个 token 的计算量只有 V3.2 的 27%，KV cache 只有 10%。
  • 混合架构：Qwen3-Next（2025 年 9 月）每 3 层 Gated DeltaNet（一种线性 attention）配 1 层 full attention，共 48 层；Qwen3.5（2026 年 2 月）整个系列沿用 3:1。Kimi Linear 按层混合 KDA 和 MLA，报告 KV cache 最多减少 75%、1M 上下文 decode 吞吐最高 6 倍。Nemotron 3 主要由 Mamba-2 层和 MoE 层交替组成，只保留极少数 attention 层。
  • 为什么不全换掉：纯线性结构的记忆容量是固定的，处理长序列、从上下文里准确找回信息都比较困难，所以保留少数全局 attention 层作为折中。
  • 也有团队退了回来：MiniMax 上一代用过 Lightning Attention 混合结构，M2 又改回全部 full attention。他们的解释是：小规模、旧评测上混合结构和纯 full attention 一样好，规模变大后复杂的多步推理明显变差；而且现有的软硬件生态越来越围绕 full attention 优化。

7.3 换了架构，推理系统要改什么

问 7.3「因为我感觉这个课程学习下来好像LLM推理系统都是围绕attention也就是KV设计的，如果是这样的话我想问换个不用attention的模型，或者attention变种，那LLM推理系统需要改变吗？」 看解答 ↓

课程里大约一半的设计围绕权重和调度，这部分基本不用改；另一半围绕 KV，要改的原因不是 attention 没了，而是 KV 的几个关键性质变了。

性质KV cache线性 attention / Mamba 的状态
大小随上下文长度增长固定
粒度每个 token 一份每个请求一份
更新方式只往后追加，旧的不变原地覆盖
能否退回到更短的前缀能，截掉后面的就行不能
课程内容换成混合架构之后
第 1 课：roofline、decode 每步读全部权重不变；“读 KV”那一项变成读一个固定大小的状态
第 2 课：continuous batching、chunked prefill不变，调度和模型结构无关
第 2 课：PagedAttentionattention 层照旧；状态层按请求分配固定槽位，两种池子的比例要能调
第 2、5 课：前缀缓存、KV 感知路由大改：状态只能在保存过的检查点上精确命中，索引记录的是检查点
第 3 课：FlashAttention线性 attention / SSM 要用自己的分块计算 kernel
第 3 课：量化、CUDA Graph基本不变；对状态做低精度存储要更小心
第 3 课：投机解码要改：被拒的草稿 token 已经改写了状态，要保存中间状态才能回退
第 4 课：TP、EP、MoE不变，MLP/MoE 那一半没变
第 5 课：P/D 传 KV、分层存储要传、要存的东西从 KV 变成“KV + 状态”
第 6 课：扩缩容、SLO、安全基本不变；容量规划按“KV + 状态”来算

用 Qwen3-Next 的公开配置估算一下（每 4 层 1 层 full attention；full attention 层 2 个 KV head、head_dim 256；线性层 32 个 value head，key / value head_dim 都是 128）：

Qwen3-Next-80B-A3B：48 层 = 12 层 full attention + 36 层 GDN

full attention 层的 KV（BF16，随长度增长）
  2 × 2 个 KV head × 256 维 × 2 字节 × 12 层 = 24 KiB / token
GDN 层的状态（BF16，固定大小）
  每层：32 × 128 × 128 × 2 字节 = 1 MiB，另有 48 KiB 卷积状态
  36 层合计 ≈ 37.7 MiB / 请求（约等于 1,600 个 token 的 KV）

一个 32K 上下文的请求：
  KV 768 MiB + 状态 37.7 MiB ≈ 806 MiB
  如果 48 层全是 full attention：3,072 MiB，约 3.8 倍
每 256 个 token 存一个状态检查点：
  这 256 个 token 的 KV 只有 6 MiB，一个检查点却要 37.7 MiB
  • 引擎的做法时效：vLLM 的 hybrid KV cache manager 按层的类型分配不同的槽位，并按层定前缀命中规则；SGLang 用可伸缩的内存池，按负载动态调整状态池和 KV 池的比例。
  • 检查点的两难（Marconi 论文）：想多命中就要频繁保存检查点，比如每 256 个 token 一个，但每个检查点都很大，而且大多用不上。上面算出一个检查点约等于 1,600 个 token 的 KV（状态用 FP32 存还要再翻一倍），所以要按“复用的可能性”和“省下的计算 ÷ 占用的显存”挑着存。
  • attention 变种看它改了 KV 的哪个性质：只改每个 token 的 KV 大小（GQA、MLA），框架不用动，只换 kernel 和 KV 布局；滑动窗口只需保留最近一个窗口的 KV，前缀命中也只要求窗口内的 KV 还在；稀疏或压缩 attention（DSA、DeepSeek-V4）会多出新的缓存种类，比如 SGLang 支持 V4 时要管 full attention 和滑动窗口两套页，外加压缩 KV、indexer 缓冲区、compressor 状态等附属池。
  • 趋势：引擎把“KV cache”抽象成“每层一种缓存，各有自己的复用规则”。SGLang 的 Unified Radix Cache 规定：full attention 的 KV 在整个匹配前缀上都能复用，滑动窗口只覆盖结尾的那个窗口，循环状态只在精确的前缀检查点上有效；新架构加一个组件即可，不用另写一套缓存树。

判断新架构的三个问题：

  1. 每个请求要存的东西，会不会随上下文长度增长？→ 决定显存管理和容量规划。
  2. 存的东西能不能截断成更短前缀的版本？→ 决定前缀缓存和投机解码怎么做。
  3. 每个 token、每个请求要存多少字节？→ 决定 P/D 之间传输和分层存储划不划算。

7.4 上下文压缩：客户端还是推理引擎

问 7.4「实际使用agent时1M的context长度比较常见，还会进行上下文压缩，这个是属于客户端的优化还是推理引擎的优化？」 看解答 ↓

两边都做，但做的是两件不同的事：agent 里说的“上下文压缩”（compaction）在客户端或 API 层，减少的是发给模型的 token；推理引擎和模型做的是“KV 压缩”，token 不变，改的是 KV 怎么存、放在哪、每步读多少。

层做什么改变了什么例子
客户端 / agent 框架把旧对话写成摘要、删掉旧的工具输出、把子任务交给子 agent发给模型的 token 变少各家 agent 自带的自动压缩
API 平台同样的事，由服务方在服务端代做同上Claude 的 compaction 和 context editing、OpenAI 的 compaction时效
推理引擎KV 量化、卸载到 CPU/SSD、前缀缓存token 不变，KV 的存法和存放位置变了vLLM 的 FP8 KV cache、LMCache
模型结构MLA、稀疏 attention、混合线性层每个 token 的 KV 变小，或者不再随长度增长DeepSeek-V4、Qwen3.5
  • 支持 1M 为什么还要压缩：上下文越长，模型准确找回信息的能力越差（context rot）；这是逐渐下降，不是突然失效。压缩同时也省钱、省延迟。
  • 常见做法：Claude 的 compaction 在服务端把旧轮次写成摘要；context editing 在 prompt 送进模型之前由服务端删掉旧的工具结果，客户端仍保留完整历史；OpenAI 的 Responses API 在 token 数超过阈值时自动压缩（文档示例的阈值是 200K）；子 agent 用几万个 token 干活，只交回 1,000 到 2,000 token 的摘要。
  • API 层的压缩虽然在服务端执行，仍属于应用层：它在 prompt 进入模型之前改 token，和推理引擎无关。
假设一个 70B、full attention 的模型能跑 1M 上下文
（参数同第 1 课的 Llama-3.1-70B，TP=8，H100，MFU 50%）

1M token 的 KV：327.7 GB，占一个 8 卡实例 KV 容量的 75%
每一轮新增 2,000 token：
  命中前缀缓存：只算新 token，prefill ≈ 1.4 秒
  没命中：整段重新 prefill ≈ 367 秒（约 6 分钟）
  decode 每步 ≈ 17.5 ms，其中读 KV 占 12.2 ms
压缩成 50K token 之后：
  重新 prefill 一次 ≈ 2.6 秒
  KV 16.4 GB（3.8%），之后每轮新增 2,000 token ≈ 0.14 秒
  • 前缀缓存是两层之间的接口：命中约 1.4 秒，不命中约 6 分钟。Manus 把 KV-cache 命中率当作生产环境 agent 最重要的单一指标；用 Claude Sonnet 时，缓存命中的输入 token 价格只有未命中的十分之一时效。做法：前缀保持稳定（差一个 token，从那里往后的缓存全部失效）；上下文只追加，不改之前的动作和观察结果；自己部署时打开前缀缓存，并用 session ID 把同一会话固定路由到同一个 worker（第 5 课的 KV 感知路由）。
  • 压缩本身会让缓存失效：改写历史后，从改动的位置往后，前缀就和以前不一样了。Claude 的文档建议每次清掉足够多的 token，让这次失效划算。
  • 所以压缩要少做，每次做得彻底：付一次重新 prefill 的代价，换来之后每轮便宜约 10 倍、KV 占用从 75% 降到 3.8%，同一个实例能服务的会话数大约多 20 倍。system prompt 和工具定义固定放在最前面，压缩之后这一段仍然能命中缓存。

第 1 课 · 推理基础

问 1.1

「decode 的算术强度为什么约等于 batch 大小 B？」（大意）

看一个线性层 Y = X · W：X 有 B 行（这一步的 B 个 token），W 是 d × d。

计算量：Y 有 B × d 个元素，每个要做 d 次乘加 → 2 × B × d² FLOP
访存：  主要是读一遍 W（BF16 每个数 2 字节）  → 2 × d² 字节
        （B 很小时，X 和 Y 的读写可以忽略）
算术强度 = 2Bd² / 2d² = B
  • 含义：权重读进来一次，能给 B 个 token 用；B 越大，每读 1 字节换来的计算越多。
  • H100 要到约 295 才喂得饱算力，decode 的 batch 通常远小于它，所以加大 batch 几乎是“白赚”吞吐，直到显存容量或 ITL 目标先顶到上限。

问 1.2

「有没有把模型权重直接做进芯片、绕开显存带宽瓶颈的推理芯片？」（大意）

有，思路都是绕开“每生成一个 token 都要把权重从显存读一遍”这个瓶颈：

  • 把权重直接做成电路：Taalas 的 HC1 把一个具体模型的权重固化在芯片里，换模型就得换芯片。
  • 把权重全放进片上 SRAM：Groq 的 LPU、Cerebras 的晶圆级芯片，用大量片上存储代替 HBM，带宽高得多，但单芯片容量有限，大模型要用很多芯片拼起来。

  • 只为 Transformer 设计的 ASIC：Etched。

代价都是灵活性或容量：模型、精度或上下文长度一变，硬件可能就不合适了。

第 2 课 · 推理引擎

问 2.1

「为什么一个请求在做 prefill，会让同一批里别人的 decode 变慢？」（大意）

  • 引擎的每一步是一个同步点：GPU 把这一步 batch 里所有请求的计算都做完，才给每个请求发出下一个 token。
  • 这一步里如果混进一个长 prompt 的 prefill，这一步的时长就由 prefill 决定，batch 里所有 decode 请求都要陪着等：8B 的例子里，从每步 12.81 ms 变成约 0.82 秒。
  • 解法：chunked prefill 把 prefill 切小，每步只多花一点时间（第 2 课）；或者干脆 P/D 分离（第 5 课）。

问 2.2

「为什么不同请求不能共享同一个没写满的 block？」（大意）

  • 一个 token 在各层的 K、V 不只取决于它自己：从第二层开始，隐藏状态里已经混进了前面所有 token 的信息。所以只有“前文完全相同、本块内容也完全相同”的块，KV 才完全相同。

第 3 课 · 单卡优化

问 3.1

「分块计算 softmax，为什么结果和整行一起算完全一样？」（大意）

  • softmax 需要整行的最大值和指数和。分块时，每块先用块内最大值算出局部结果，同时记下 (m, l)。
  • 合并时，把各块的指数和“换算”到同一个最大值下，也就是乘上 exp(mi − m)。这是恒等变形，不是近似：
整行：l = Σ exp(s − m)
        = exp(m1 − m) · Σ块1 exp(s − m1) + exp(m2 − m) · Σ块2 exp(s − m2)
        = exp(m1 − m) · l1 + exp(m2 − m) · l2
输出同理：o = Σ exp(s − m) · v / l
            = [exp(m1 − m) · l1 · o1 + exp(m2 − m) · l2 · o2] / l

好处是不必把整行分数存下来，一块一块流过片上 SRAM 就行；减去最大值也保证了数值稳定。

问 3.2

「speculative decoding的公式推导格式不对，没有正确展示；第三步“等比数列求和”这一段显示不完全」

完整推导：

设每个草稿 token 被接受的概率都是 α，一次猜 k 个。
验证时从第一个开始逐个检查，遇到第一个被拒绝的就停下，由大模型在这个位置补一个 token；
k 个全被接受时，大模型额外再生成一个。

第一步：这一步产出的 token 数 = 被接受的前缀长度 + 1
第二步：前 i 个都被接受的概率是 αi，所以
        期望产出 = 1 + α + α2 + … + αk
第三步：等比数列求和
        设    S = 1 + α + α2 + … + αk
        那么 αS =     α + α2 + … + αk + αk+1
        两式相减：S − αS = 1 − αk+1
        所以：     S = (1 − αk+1) / (1 − α)

例：α = 0.8，k = 4：S = (1 − 0.85) / 0.2 = (1 − 0.32768) / 0.2 ≈ 3.36

问 4.2

「抱歉，帮我回想一下这个细节。prefill阶段算力是瓶颈，所以TTFT的下限大概是2*k*d*d*权重精度字节数/算力。（K维度是k*d, V维度是d*d）decode阶段显存带宽是瓶颈，TPOT的下限应该等于生成一个token所需的显存/带宽。为什么是用权重字节数作为被除数呢？权重不是只需要load一次吗？」

  • 权重并不会留在芯片上：GPU 的片上存储（H100 的 L2 缓存 50 MB，加上各 SM 的共享内存和寄存器，合计也只有一百多 MB）远放不下 8B 的 16 GB、70B 的 141 GB 权重。权重平时待在显存（HBM）里，每生成一个 token，都要把全部权重从 HBM 搬进计算单元一遍——不是只读一次。
  • 所以 decode 每步时间下限 ≈（全部权重字节 + 这一步要读的全部 KV 字节）÷ 显存带宽。batch 里的多个请求可以共用这一次读取，这正是加大 batch 能提高吞吐的原因。
  • prefill 的下限公式要改一下：计算量只看乘加次数，约为 2 × 参数量 × prompt 的 token 数，再除以峰值算力；不需要乘“权重精度字节数”——字节数决定的是读数据的时间，不是计算量。

问 4.3

「解释一下TP里的每一层是指什么？以transformer based模型为例，每一层对应softmax（Q*K*缩放）*Vt的哪一个？」

  • “每一层”指一个完整的 Transformer 层（block），不是 attention 里的某一个矩阵乘：一层 = attention 块 + MLP 块（再加上各自的 RMSNorm 和残差）。softmax(QKᵀ/√d)·V 只是 attention 块中间的一步。
  • TP 在每一层内部切：attention 块按 head 切，每张卡负责一部分 head，各自算 Q、K、V、softmax 和加权求和（不同 head 之间互不依赖），再乘自己那一份 W_O，最后 all-reduce；MLP 块按“W_up 按列、W_down 按行”切，最后 all-reduce。

问 4.4

「理论上每一层的输入应该是上一层完整的输出对吗？那在TP里是不是每个GPU都要先算完第i层的部分输出，然后所有gpu的输出汇总成完整的输出，再执行下一层？」

对。每一块都需要完整的输入，TP 的切法保证了这一点：

attention 块：各卡算自己那部分 head → 各得一份“部分和”
  → all-reduce：把各卡的部分和加起来，并让每张卡都拿到完整结果
MLP 块：      各卡用完整输入算自己那一份 → 部分和
  → all-reduce
→ 进入下一层（每层 2 次 all-reduce）

all-reduce = 求和 + 广播。它是一个同步点，所以每层的通信时间直接加在每一步上，TP 要放在 NVLink 这类高速互联上。

问 4.6

「RMSnorm、输出投影、残差、Wgate是干嘛的？」

  • RMSNorm：把每个 token 的向量按均方根缩放到稳定的尺度（再乘一个可学习的系数 g），防止数值一层层越传越大或越小。
RMSNorm(x) = x / √(mean(x²) + ε) ⊙ g
  • 输出投影 W_O：把各个 head 的输出拼起来后，用 W_O 再混合回 d 维，让不同 head 的信息互相融合。
  • 残差：把块的输入直接加到输出上（x + f(x)），信息和梯度可以绕过这一块直接往下传，深层网络才训得动。
  • W_gate：SwiGLU 里的门控。SiLU(x·W_gate) 与 x·W_up 逐元素相乘，决定每个维度“放行多少”，比普通的“升维—激活—降维”效果更好。

问 4.7

「详细解释这个公式的每一个符号」

X         这一步输入的激活矩阵：行数 = token 数，列数 = d（隐藏维度）
W_up      升维矩阵，d × d_ff（d_ff 通常是 d 的几倍）
act       激活函数（如 SiLU），逐元素计算
W_down    降维矩阵，d_ff × d
n         TP 的卡数
W_up_b    W_up 按列切出的第 b 块，d × (d_ff / n)
W_down_b  W_down 按行切出的第 b 块，(d_ff / n) × d
Y         输出，形状和 X 一样
  • 为什么切开算和不切完全一样：矩阵乘法可以沿中间那一维拆开求和，[A1 … An] · [B1; …; Bn] = Σ AbBb。
  • act 是逐元素的，所以 act(X·W_up) 的第 b 块列只取决于 W_up_b，每张卡只需要自己那一份；最后 all-reduce 把 n 个部分和加起来，就是完整的 Y。

问 4.8

「GQA是什么」

  • GQA（Grouped-Query Attention，分组查询注意力）：把 query head 分成若干组，每组共用一个 K head 和一个 V head。
  • 它介于两个极端之间：每个 query head 都有自己的 K、V（MHA，标准多头注意力），和所有 query head 共用一组 K、V（MQA）。只有 1 组时就是 MQA，组数等于 head 数时就是 MHA。
  • Llama-3.1-8B：32 个 query head、8 个 KV head，KV 是 MHA 的 1/4；70B：64 个 query head、8 个 KV head，KV 是 MHA 的 1/8。质量接近 MHA，KV 小很多，decode 每步要读的数据也少很多。

问 4.9

「EP没太看懂，重讲一次」

用一个能手算的例子：

4 张卡，8 个专家：卡 0 放专家 0、1，卡 1 放专家 2、3，卡 2 放 4、5，卡 3 放 6、7
每张卡上各有一批 token；每个 token 由路由器选 2 个专家（top-2）

1. 路由：每张卡给自己的 token 算出该去哪两个专家
2. 分发（all-to-all）：把 token 发到对应专家所在的卡
3. 计算：每张卡用自己的专家，处理收到的所有 token
4. 合并（all-to-all）：把结果送回 token 原来所在的卡，按路由权重加权求和
  • 好处：每个专家能收集到所有卡送来的 token，batch 变大；权重分散开，每张卡的显存压力小。
  • 代价：每个 MoE 层两次 all-to-all，跨机时依赖高速网络；专家冷热不均时还要做负载均衡。

问 4.10

「这下看懂了，那卡间通信、机间通信是谁实现的？推理引擎吗」

分工是：推理引擎决定“什么时候、和谁、交换什么”，具体搬数据交给通信库和硬件。

  • 引擎：比如 TP 每层两次 all-reduce、EP 每层两次 all-to-all、PP 段间收发、P/D 之间传 KV。
  • 通信库：NCCL 做 all-reduce、all-gather 等集合通信；vLLM 等引擎还有自己针对小消息的 all-reduce kernel；DeepEP 专门优化 MoE 的 all-to-all；NVSHMEM 让 GPU 直接读写其他 GPU 的显存；KV 传输用 NIXL、Mooncake 的 Messenger 等。
  • 硬件：机内走 NVLink / NVSwitch；机间走 InfiniBand 或 RoCE 网卡，配合 GPUDirect RDMA 让网卡直接读写显存（第 5 课问 5.3）。

问 5.1

「这个dynamo的算法为何只考虑decode的负载？prefill的负载不用考虑吗？」

  • 要考虑，Dynamo 也考虑了。第 5 课最初把公式写简化了：prefill 项不只是新请求要新算的块，还包括这个实例上已经分过来、还没算完的 prefill（积压）。请求输出第一个 token 时，它的 prompt 才从积压里扣掉。
  • 文档的例子里刚好没有积压，看上去就像只算了 decode 负载。给实例 2 加上 12 块积压，选择就会从实例 2 变成实例 3（见正文的例子）。
  • 两项各管一个瓶颈：prefill 项对应算力，影响新请求自己的 TTFT；decode 项（活跃 KV 块数）对应显存带宽和容量，影响这个实例上所有请求的 ITL。
  • P/D 分离后才“各算各的”：prefill 池的路由只看 prefill 项，decode 池只看活跃 KV 块、不看缓存命中。
  • 其他做法：Mooncake 直接估算 TTFT（排队时间 + 本次 prefill 时间 + 需要时的 KV 传输时间）；llm-d 用多个打分器加权（前缀命中、队列长度、KV 占用率等）。

问 5.2

「算完一层是什么意思？」

  • “一层”指模型的一层（Transformer 层），不是 KV 块，也不是 chunked prefill 的一段 token。
  • prefill 时，所有 prompt token 一起从第 1 层算到第 80 层；第 i 层的 K、V 只取决于第 i 层的输入，算完后不会再变，所以可以马上交给网卡发走，GPU 接着算下一层。
70B，TP=8，4K prompt，每张卡一张 50 GB/s 网卡：
  每层计算约 0.948 ms；每层每卡要发 2.10 MB，约 0.042 ms
  不重叠：  75.85 + 3.36  ≈ 79.2 ms
  逐层重叠：75.85 + 0.042 ≈ 75.9 ms（只剩最后一层的传输露在外面）
  • 计算用 GPU 的计算单元，发送由网卡借助 GPUDirect RDMA 直接读显存，是两套硬件；prefill 受算力限制，显存带宽还有富余，所以能同时进行。
  • 实现上：Mooncake 逐层加载、逐层存储；vLLM 的 KV connector 接口有逐层的钩子（save_kv_layer、wait_for_layer_load）。但 vLLM 的 NixlConnector 默认是 prefill 全部算完后，再由 decode 实例把 KV 拉过去，并不逐层发时效。2026 年 10 月 vLLM 又介绍了由 prefill 端主动推送 KV 的 NIXL push connector（见延伸阅读）。
  • 逐层发的前提是 prefill 开始前就选好 decode 实例、分配好接收的块；推迟到 prefill 之后再选 decode 实例，路由更灵活。

问 5.3

「RDMA就是GPU直接读网卡？怎么比SSD快这么多？GPU不能直接读SSD吗？」

  • RDMA 不是 GPU 去读网卡，而是网卡直接读写内存：本机网卡直接从远端机器的内存取数据，再直接写进本机显存（这一步叫 GPUDirect RDMA）。两端的 CPU 都不参与搬运，也没有中间拷贝。
  • 远端池快，是因为另一头不是一块盘：数据放在很多台机器的内存里（Mooncake），或分散在成百上千块 SSD 上（3FS），一起往外送，瓶颈落在本机网卡的 50 GB/s。而一块 NVMe SSD 只接 4 条 PCIe 通道：PCIe 4.0 x4 上限约 7.9 GB/s，5.0 x4 约 15.8 GB/s。
  • 3FS 的实测：180 个存储节点、每个节点 16 块 NVMe SSD，总读吞吐约 6.6 TiB/s，平均每节点约 37.5 GiB/s；作 KV cache 时，每台客户端一张 400 Gb/s 网卡，峰值读吞吐能到 40 GiB/s。
  • GPU 可以直接读 SSD：GPUDirect Storage（GDS）让 SSD 的 DMA 直接写进显存，省掉 CPU 内存里的中转，但快不过那块 SSD 本身；想更快只能多块盘一起读。
  • 注意前提：第 5 课表里“远端 50 GB/s”假设远端足够大、能把网卡喂满；如果远端只有一块 SSD，走 RDMA 也只有那块盘的速度。按 PCIe 4.0 x4 的上限算，至少要 7 块盘一起读，才喂得满一张 400G 网卡。

第 6 课 · 生产化

问 6.1

「ITL是啥缩写？」

ITL 是 Inter-Token Latency（token 间延迟）：流式输出时，相邻两次输出之间隔了多久。几个常一起出现的缩写：

缩写全称衡量什么
TTFTTime To First Token从请求到达，到第一个 token 出来
ITLInter-Token Latency相邻两次输出之间的间隔
TPOTTime Per Output Token一个请求平均每个输出 token 花的时间
E2EEnd-to-End latency从请求到达，到最后一个 token 出来
ITL： 每两次相邻输出之间记一个样本
TPOT：每个请求结束时算一次
      TPOT = (E2E 延迟 − TTFT) / (输出 token 数 − 1)

每次输出只含 1 个 token 时两者近似相等；一次输出含多个 token（比如投机解码一次接受好几个）时就不一样。从用户角度看：TTFT 决定多久开始回答，ITL 决定回答吐字有多快。

问 6.2

「MFU是啥？」

MFU 是 Model FLOPs Utilization（模型算力利用率）：模型实际完成的有效计算量，占硬件峰值算力的比例。

MFU = 模型实际完成的有效计算量（FLOP/s） / 硬件峰值算力（FLOP/s）
例：H100 的 BF16 峰值是 989.4 TFLOPS，MFU 50% 表示实际只用到约 494.7 TFLOPS
  • 到不了 100%：kernel 效率有限、要等显存读写、TP 通信、调度空隙，都会吃掉一部分算力。
  • 它和 nvidia-smi 的 GPU 利用率不是一回事：后者只看“有没有 kernel 在跑”，MFU 看的是“真正做了多少有用的计算”。

问 6.3

「你这个单位换算正确吗？？」

换算是对的。容易起疑，是因为 141.2 这个数出现了两次：权重 141.2 GB，每个 token 的计算量 141.2 GFLOP。两者单位不同，只是恰好都等于 2 × 70.6B。

70.6B 的 B 是 billion（10 亿个参数），不是字节；GFLOP 的 G 也是 10 亿
每个 token 的计算量：2 FLOP/参数 × 70.6e9 个参数 = 141.2e9 FLOP = 141.2 GFLOP
权重的大小（BF16）：  2 字节/参数 × 70.6e9 个参数 = 141.2e9 字节 = 141.2 GB
  • 每个参数 2 FLOP：每个权重对每个 token 做一次乘法、一次加法。权重“乘 2”则是因为 BF16 每个参数占 2 字节。两个“2”含义不同，数值相同纯属巧合。
  • FLOP 是运算次数，FLOPS（FLOP/s）是每秒运算次数；运算次数和 GB 一样按 1000 进制，只有 KiB、MiB 这类是 1024 进制。

第 7 节 · 新架构与新负载

问 7.1

「我可以把transformer结构等同于attention吗？」

不能。attention 是 Transformer 的一个部件（最关键的创新），负责 token 之间交换信息；每层另有一块 MLP 负责每个 token 各自加工，而且参数大头在 MLP（Llama-3.1-8B：attention 16.7%、MLP 70.2%、embedding 13.1%）。对推理来说，KV cache 只来自 attention，读权重主要读的是 MLP。详见正文 7.1。

问 7.2

「那2025年之后的主流模型都是transformer架构吗？」

问 7.3

「因为我感觉这个课程学习下来好像LLM推理系统都是围绕attention也就是KV设计的，如果是这样的话我想问换个不用attention的模型，或者attention变种，那LLM推理系统需要改变吗？」

要改大约一半。和权重、调度有关的（roofline、continuous batching、量化、TP/EP、P/D 分离的出发点、扩缩容）基本不变；围绕 KV 的（PagedAttention、前缀缓存、投机解码的回退、P/D 传 KV、分层存储）要扩展，因为状态是固定大小、原地覆盖、不能截断成更短前缀的。attention 变种看它改了 KV 的哪个性质：只改大小（GQA、MLA）几乎不用动，滑动窗口和稀疏或压缩 attention 会多出新的缓存规则。详见正文 7.3。

问 7.4

「实际使用agent时1M的context长度比较常见，还会进行上下文压缩，这个是属于客户端的优化还是推理引擎的优化？」

两边都有，但是两件事。agent 的上下文压缩（写摘要、删旧工具输出、子 agent）在客户端或 API 层，减少的是 token；引擎和模型做的是 KV 压缩（量化、卸载、MLA、稀疏 attention），token 不变。两层通过前缀缓存相连：客户端让上下文只追加、少改历史，引擎才能复用 KV；压缩本身会让缓存失效，所以要少做、每次做得彻底。详见正文 7.4。
